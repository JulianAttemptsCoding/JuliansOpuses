## Problem

LaTeXRenderer is a free collaborative LaTeX environment for a team of up to ten people, delivered from [GitHub Pages](https://pages.github.com/). That choice of host is where the problem comes from.

GitHub Pages is static file hosting. It cannot authenticate anyone, it cannot keep a secret, and nothing shipped from it is hidden. A "password-protected" static site that checks the password in JavaScript protects nothing: the check, and whatever it guards, is already in the visitor's browser.

## What the shell can and cannot do

I kept the public repository small on purpose, and wrote down what it cannot do.

- It **cannot** hide the shared password, hide the editor bundle, or decide who is allowed in. So none of those things live there.
- It **can** collect a Google identity, forward a password attempt to a server that knows how to check it, and refuse to execute application bytes that do not match the fingerprints the server published.

Sign-in uses [Supabase](https://supabase.com/) Auth with Google OAuth and PKCE, verified server-side. The shared password is checked in an Edge Function with PBKDF2, a constant-time comparison and rate limiting, and a success writes a grant row that expires. The editor bundle sits in a private storage bucket and is reachable only through five-minute signed URLs, issued after the grant is checked again. Before running anything, the shell hashes every downloaded asset and compares it with the manifest.

## Testing the attacks

Before calling it secure, I tried to break it. The [Playwright](https://playwright.dev/) suite tests four client-side bypasses one by one: deleting the password form in DevTools, setting a local-storage flag, calling shell functions from the console, and requesting the private bucket directly. All four fail. The shell doesn’t stop them; there is simply nothing in the shell worth reaching.

Around that sit Vitest unit tests for integrity verification, lint rules that ban `innerHTML` and `eval` in the shell, a build that refuses to start if it is handed a service-role key, and a CI step that scans the built output for credential material before publishing.

## Two modes

The mode is chosen at build time. Production uses Supabase as described above. A direct mode exists as an encrypted offline fallback: the editor ships as public ciphertext and is decrypted locally with the shared password. It holds no server-side data and grants no privileged action, but public ciphertext can be attacked offline, so it is documented as weaker and is not what production runs.
